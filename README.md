# harden_ssh.sh — инструкция по применению

## Назначение

Скрипт `harden_ssh.sh` настраивает SSH-сервер на Linux так, что:

- вход возможен **только по SSH-ключу**, вход по паролю отключён;
- вход под пользователем **root** запрещён;
- число попыток входа за одно подключение ограничено тремя;
- права на `~/.ssh` и `~/.ssh/authorized_keys` выставлены безопасно (700 и 600);
- ваш публичный ключ установлен пользователю.

Перед применением скрипт проверяет новую конфигурацию. При любой ошибке он отменяет изменения конфигурации и останавливается. Повторный запуск ничего не меняет, если всё уже настроено.

## 1. Обязательные правила

1. **Вход по паролю отключается для всех пользователей сервера.** Каждый, кто входит на сервер, должен иметь ключ. Ключи других людей добавляются по разделу 5.
2. **Не закрывайте открытое SSH-подключение к серверу**, пока не проверите вход по ключу в отдельном окне (шаг 3.8). Скрипт не обрывает открытые подключения, поэтому оно остаётся запасным входом.
3. **На сервер копируется только публичный ключ** — файл с окончанием `.pub`. Файл ключа без `.pub` (приватный ключ) никогда не копируйте и никому не передавайте.
4. **Выполняйте шаги строго по порядку.** Каждый шаг заканчивается проверкой результата. Если результат не совпадает с ожидаемым, не переходите к следующему шагу: найдите сообщение в разделе 7.

## 2. Что нужно заранее

| Что | Где взять |
|---|---|
| файл `harden_ssh.sh` | в папке проекта |
| адрес сервера (IP или имя) | у администратора / хостинга / в настройках ВМ |
| имя вашего пользователя на сервере и его пароль | у администратора / задаётся при установке системы |
| у этого пользователя есть право `sudo` | проверяется в шаге 3.3 |
| запасной доступ к серверу без SSH | консоль виртуальной машины или веб-консоль хостинга |

Если на сервере у вас есть **только пользователь root**, сначала выполните раздел 4.

Команды вводятся в двух местах:

| Где | Система | Какие команды |
|---|---|---|
| **ваш компьютер** | Linux, macOS или Windows 10/11 (PowerShell) | `ssh`, `scp`, `ssh-keygen`, `docker` — одинаковы во всех системах; отличается только задание параметров (шаг 3.1) |
| **сервер** | только Linux | всё, что выполняется после входа на сервер; такие шаги помечены «На сервере» |

## 3. Настройка сервера: пошаговая процедура

### 3.1. Задайте параметры подключения

Откройте терминал на своём компьютере. Скопируйте блок, **замените значения в кавычках на свои** и выполните его.

**Linux / macOS:**
```bash
SERVER="192.168.1.50"           # адрес сервера
SSH_USER="admin"                # ваш пользователь на сервере
PORT="22"                       # порт SSH (обычно 22)
KEY=~/.ssh/id_ed25519.pub       # ваш публичный ключ
```

**Windows (PowerShell):**
```powershell
$SERVER   = "192.168.1.50"
$SSH_USER = "admin"
$PORT     = "22"
$KEY      = "$HOME\.ssh\id_ed25519.pub"
```

Все следующие команды на вашем компьютере используют эти параметры и **вводятся без изменений**.

> Виртуальная машина VirtualBox с пробросом порта (например, порт хоста 2222 на порт 22 гостя): `SERVER="localhost"`, `PORT="2222"`.

### 3.2. Проверьте наличие SSH-ключа

```bash
ls "$KEY"
```

| Результат | Действие |
|---|---|
| выведен путь к файлу | ключ есть, переходите к 3.3 |
| `No such file or directory` / `Cannot find path` | создайте ключ командой ниже, затем повторите `ls "$KEY"` |

Создание ключа (на все вопросы нажимайте Enter):
```bash
ssh-keygen -t ed25519
```

> Если у вас уже есть ключ с другим именем (например, `id_rsa.pub`), укажите его в `KEY` (шаг 3.1) вместо создания нового.

### 3.3. Проверьте подключение к серверу и права sudo

```bash
ssh -t -p "$PORT" "${SSH_USER}@${SERVER}" "sudo -v && echo SUDO_OK"
```

Последовательно будут запрошены:
1. при первом подключении — подтверждение `Are you sure you want to continue connecting (yes/no)?` — введите `yes`;
2. пароль пользователя для входа по SSH;
3. пароль для `sudo` (обычно тот же).

| Результат | Действие |
|---|---|
| в конце выведено `SUDO_OK` | переходите к 3.4 |
| `Connection refused` / `Connection timed out` | SSH-сервер не установлен или неверный адрес/порт — см. раздел 7 |
| `is not in the sudoers file` | у пользователя нет права sudo — обратитесь к администратору сервера |

### 3.4. Скопируйте скрипт и ключ на сервер

Перейдите в папку, где лежит `harden_ssh.sh`:
```bash
cd ПУТЬ/К/ПАПКЕ/СО/СКРИПТОМ
```
Скопируйте файлы:
```bash
scp -P "$PORT" harden_ssh.sh "${SSH_USER}@${SERVER}:/tmp/harden_ssh.sh"
scp -P "$PORT" "$KEY" "${SSH_USER}@${SERVER}:/tmp/key.pub"
```
Ожидаемый результат: для каждого файла строка с `100%`.

### 3.5. Подключитесь к серверу (окно 1)

```bash
ssh -p "$PORT" "${SSH_USER}@${SERVER}"
```
**Это окно не закрывайте до завершения шага 3.8.** Шаги 3.6 и 3.7 выполняются в нём, то есть **на сервере**.

### 3.6. На сервере: проверьте план изменений

```bash
sudo bash /tmp/harden_ssh.sh -u "$USER" -k /tmp/key.pub -n
```
Ничего не изменяется, выводится только план.

Ожидаемый результат: нет строк `[fail]`, последняя строка — `Будет изменено: N`.

> `"$USER"` вводится как есть: на сервере это имя пользователя, под которым вы вошли.

### 3.7. На сервере: примените настройки

```bash
sudo bash /tmp/harden_ssh.sh -u "$USER" -k /tmp/key.pub
```

Ожидаемый результат — в конце вывода:
```
[ ok ] Синтаксис конфигурации корректен (sshd -t)
[ ok ] Фактические значения совпадают с нужными (sshd -T)
...
[info] Готово. Изменений: N
```

Если выведено `[fail]`: изменения конфигурации уже отменены автоматически. Найдите текст ошибки в разделе 7.

### 3.8. Проверьте вход (окно 2)

Откройте **новое** окно терминала на своём компьютере. Выполните в нём блок параметров из шага 3.1, затем три команды:

```bash
ssh -p "$PORT" "${SSH_USER}@${SERVER}" "echo KEY_LOGIN_OK"
ssh -p "$PORT" -o PubkeyAuthentication=no "${SSH_USER}@${SERVER}"
ssh -p "$PORT" "root@${SERVER}"
```

| Команда | Ожидаемый результат |
|---|---|
| первая (вход по ключу) | выведено `KEY_LOGIN_OK`, пароль **не** запрашивался |
| вторая (попытка входа по паролю) | `Permission denied (publickey)` |
| третья (вход под root) | `Permission denied (publickey)` |

> Если ключ создан с парольной фразой, ssh запросит `Enter passphrase for key` — это пароль от ключа, а не от сервера; введите его.

- **Все три результата совпали** — настройка выполнена успешно. Переходите к 3.9.
- **Первая команда завершилась `Permission denied (publickey)`** — вернитесь в окно 1 и выполните раздел 6 (отмена изменений). Затем проверьте, что в шаге 3.4 был скопирован ваш ключ из `KEY`.

### 3.9. На сервере (окно 1): сохраните скрипт и удалите временные файлы

```bash
sudo install -m 755 /tmp/harden_ssh.sh /usr/local/sbin/harden_ssh.sh
rm /tmp/harden_ssh.sh /tmp/key.pub
exit
```
Скрипт остаётся на сервере в `/usr/local/sbin/harden_ssh.sh` для обслуживания (раздел 5).

**Настройка завершена.** Вход на сервер выполняется командой:
```bash
ssh -p "$PORT" "${SSH_USER}@${SERVER}"
```

## 4. Если на сервере есть только пользователь root

Так часто бывает на арендованных серверах (VPS). Вход под root скрипт запрещает, поэтому сначала создайте обычного пользователя с правом `sudo`.

**На сервере, под root.** Замените `admin` на нужное имя.

Ubuntu / Debian:
```bash
adduser admin
usermod -aG sudo admin
```

RHEL / Rocky / AlmaLinux / Fedora:
```bash
useradd -m admin
passwd admin
usermod -aG wheel admin
```

Пароль, заданный здесь, будет использоваться для `sudo`. Вход по SSH после настройки будет только по ключу.

Далее выполните раздел 3, указав в шаге 3.1 `SSH_USER="admin"`.

## 5. Обслуживание: добавить ключ, проверить настройки

Все команды — **на сервере**, после входа по ключу.

### Добавить ключ другого человека или другого вашего компьютера

1. Получите от человека его **публичный** ключ (файл `.pub`) и скопируйте его на сервер в `/tmp/new_key.pub` (как в шаге 3.4).
2. На сервере:
   ```bash
   sudo /usr/local/sbin/harden_ssh.sh -u "$USER" -k /tmp/new_key.pub
   rm /tmp/new_key.pub
   ```
   Ожидаемый результат: `[chg ] Добавить ключ …`, затем `Готово. Изменений: 1`.

Чтобы выдать доступ **отдельному пользователю**, укажите его имя в `-u`. Если такого пользователя нет, скрипт его создаст:
```bash
sudo /usr/local/sbin/harden_ssh.sh -u ivanov -k /tmp/new_key.pub
```

### Проверить, что настройки не изменились (например, после обновления системы)

```bash
sudo /usr/local/sbin/harden_ssh.sh -u "$USER"
```
Ожидаемый результат: `Готово. Система уже в нужном состоянии, изменений нет`.
Если какие-то настройки были изменены, скрипт вернёт их к безопасным значениям.

## 6. Отмена изменений

При ошибке скрипт отменяет изменения конфигурации автоматически. Ручная отмена нужна, только если требуется вернуть прежние настройки после успешного запуска.

Если вход по SSH уже невозможен, выполняйте команды через консоль виртуальной машины или веб-консоль хостинга.

**Шаг 1.** Удалите файл с настройками:
```bash
sudo rm /etc/ssh/sshd_config.d/00-hardening.conf
```

**Шаг 2.** Примените изменения — одной командой, соответствующей вашей системе:

| Система | Команда |
|---|---|
| Ubuntu, Debian | `sudo systemctl reload ssh` |
| RHEL, Rocky, AlmaLinux, Fedora | `sudo systemctl reload sshd` |
| Alpine, Gentoo, Devuan (OpenRC) | `sudo rc-service sshd reload` |
| Void (runit) | `sudo sv reload sshd` |

**Если файла `00-hardening.conf` нет** (старые системы, где скрипт изменял основной файл `/etc/ssh/sshd_config`), восстановите основной файл из резервной копии. Путь к копии скрипт выводит в конце работы (`Резервная копия: …`):
```bash
sudo ls /var/backups/ssh-hardening/
sudo cp -a /var/backups/ssh-hardening/ИМЯ_ПАПКИ/etc/ssh/sshd_config /etc/ssh/sshd_config
```
затем выполните шаг 2.

Права на `~/.ssh` и добавленные ключи при отмене не изменяются.

## 7. Ошибки и их устранение

### Сообщения скрипта

| Сообщение | Причина | Устранение |
|---|---|---|
| `Скрипт нужно запускать от root (sudo)` | команда без `sudo` | добавьте `sudo` в начало команды |
| `Укажите пользователя: -u USER` | не указан `-u` | введите команду в точности как в инструкции |
| `Пользователь для входа не может быть root` | вы вошли на сервер под root | выполните раздел 4 |
| `Не удаётся прочитать /tmp/key.pub` | ключ не скопирован | повторите шаг 3.4 |
| `/tmp/key.pub не похож на публичный SSH-ключ` | скопирован не тот файл | проверьте, что `KEY` указывает на файл `.pub`, повторите шаг 3.4 |
| `У … нет ни одного ключа` | не указан `-k` и у пользователя нет ключей | добавьте `-k /tmp/key.pub` |
| `Не найден sshd — установите openssh-server` | SSH-сервер не установлен | см. «SSH-сервер не установлен» ниже |
| `sshd -t отклонил конфигурацию` | ошибка в настройках SSH | изменения уже отменены; сохраните вывод и передайте администратору |
| `Часть параметров перекрыта другими настройками` | другой файл в `/etc/ssh/sshd_config.d/` задаёт те же параметры раньше | в выводе указан файл и строка; удалите эту строку и запустите скрипт снова |
| `[warn] Запущенный sshd не найден` | SSH-сервер сейчас не запущен | не ошибка: настройки вступят в силу при его запуске |

### Сообщения при подключении

| Сообщение | Причина | Устранение |
|---|---|---|
| `Connection refused` | SSH-сервер не запущен или неверный порт | проверьте `PORT`; см. «SSH-сервер не установлен» |
| `Connection timed out` / `No route to host` | неверный адрес или сервер недоступен | проверьте `SERVER` и что сервер включён |
| `Permission denied (publickey)` при входе по ключу | на сервер скопирован другой ключ, или ssh не нашёл ваш ключ | укажите ключ явно: `ssh -i ~/.ssh/id_ed25519 -p "$PORT" "${SSH_USER}@${SERVER}"` |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | сервер переустановлен | если сервер ваш и его действительно переустанавливали: `ssh-keygen -R "$SERVER"` (для нестандартного порта: `ssh-keygen -R "[${SERVER}]:${PORT}"`) |

### SSH-сервер не установлен

Выполните через консоль сервера (окно ВМ или веб-консоль хостинга):

| Система | Команда |
|---|---|
| Ubuntu, Debian | `sudo apt update && sudo apt install -y openssh-server` |
| RHEL, Rocky, AlmaLinux, Fedora | `sudo dnf install -y openssh-server && sudo systemctl enable --now sshd` |
| Alpine | `apk add openssh bash coreutils shadow && rc-update add sshd && rc-service sshd start` |

## 8. Сервер в Docker-контейнере

Для контейнера, внутри которого работает SSH-сервер. В контейнере должны быть установлены `bash` и `openssh-server`.

### 8.1. Задайте параметры

Linux / macOS (в Windows PowerShell задайте те же параметры в форме `$CONTAINER = "my-ssh"`, как в шаге 3.1):
```bash
CONTAINER="my-ssh"              # имя контейнера (см. docker ps)
SSH_USER="admin"                # пользователь для входа (будет создан, если его нет)
PORT="2222"                     # порт на вашем компьютере, проброшенный на порт 22 контейнера
KEY=~/.ssh/id_ed25519.pub       # ваш публичный ключ
```

### 8.2. Скопируйте скрипт и ключ в контейнер

Из папки со скриптом:
```bash
docker cp harden_ssh.sh "$CONTAINER":/tmp/harden_ssh.sh
docker cp "$KEY" "$CONTAINER":/tmp/key.pub
```
Только для Linux: если `docker cp` выдаёт ошибку доступа (Docker, установленный через snap), используйте вместо этого:
```bash
cat harden_ssh.sh | docker exec -i "$CONTAINER" sh -c 'cat > /tmp/harden_ssh.sh'
cat "$KEY"        | docker exec -i "$CONTAINER" sh -c 'cat > /tmp/key.pub'
```

### 8.3. Проверьте план и примените

```bash
docker exec "$CONTAINER" bash /tmp/harden_ssh.sh -u "$SSH_USER" -k /tmp/key.pub -n
docker exec "$CONTAINER" bash /tmp/harden_ssh.sh -u "$SSH_USER" -k /tmp/key.pub
```
Ожидаемый результат: `Готово. Изменений: N`.

### 8.4. Проверьте вход

```bash
ssh -p "$PORT" "${SSH_USER}@localhost" "echo KEY_LOGIN_OK"
ssh -p "$PORT" -o PubkeyAuthentication=no "${SSH_USER}@localhost"
ssh -p "$PORT" root@localhost
```
Ожидаемые результаты — как в шаге 3.8.

Команда `docker exec` работает без SSH, поэтому доступ к контейнеру сохраняется при любом результате.

### 8.5. Постоянная настройка

Изменения, сделанные в работающем контейнере, **теряются при пересоздании контейнера**. Чтобы настройки входили в образ, добавьте в `Dockerfile` после установки `openssh-server`:

```dockerfile
COPY harden_ssh.sh /usr/local/sbin/harden_ssh.sh
COPY id_ed25519.pub /tmp/key.pub
RUN bash /usr/local/sbin/harden_ssh.sh -u admin -k /tmp/key.pub && rm /tmp/key.pub
```
Файлы `harden_ssh.sh` и `id_ed25519.pub` должны лежать рядом с `Dockerfile`. При сборке будет выведено `[warn] Запущенный sshd не найден` — это ожидаемо: настройки вступят в силу при запуске контейнера.

## 9. Справочник

### 9.1. Параметры запуска

```
sudo bash harden_ssh.sh -u ПОЛЬЗОВАТЕЛЬ [-k КЛЮЧ.pub] [-n] [-c ФАЙЛ] [-f]
```

| Параметр | Описание |
|---|---|
| `-u`, `--user ИМЯ` | Обязательный. Пользователь, которому настраивается вход по ключу. Не может быть `root`. Если пользователя нет, он создаётся |
| `-k`, `--pubkey ФАЙЛ` | Файл с публичным ключом (ключами — по одному в строке). Ключи добавляются в `authorized_keys`, повторы пропускаются |
| `-n`, `--dry-run` | Показать план изменений, ничего не изменяя |
| `-c`, `--config ФАЙЛ` | Использовать свой набор настроек SSH вместо встроенного (см. 9.4) |
| `-f`, `--force` | Продолжить, если у пользователя нет ни одного ключа. Использовать только при наличии консольного доступа к серверу |
| `-h`, `--help` | Справка |

### 9.2. Обозначения в выводе

| Метка | Значение |
|---|---|
| `[ ok ]` | проверено, изменений не требуется |
| `[chg ]` | изменение внесено |
| `[plan]` | изменение будет внесено (режим `-n`) |
| `[info]` | информация |
| `[warn]` | предупреждение, работа продолжается |
| `[fail]` | ошибка, работа остановлена, изменения конфигурации отменены |

### 9.3. Что изменяет скрипт

Настройки записываются в файл `/etc/ssh/sshd_config.d/00-hardening.conf`. Основной файл `/etc/ssh/sshd_config` не изменяется. На старых системах, где SSH-сервер не поддерживает каталог `sshd_config.d`, настройки записываются в начало `/etc/ssh/sshd_config` между строками-метками `# >>> ssh-hardening` и `# <<< ssh-hardening`.

| Параметр | Значение | Назначение |
|---|---|---|
| `PermitRootLogin` | `no` | запрет входа под root |
| `PasswordAuthentication` | `no` | запрет входа по паролю |
| `KbdInteractiveAuthentication` | `no` | запрет альтернативного ввода пароля |
| `PermitEmptyPasswords` | `no` | запрет входа без пароля |
| `PubkeyAuthentication` | `yes` | вход по ключу разрешён |
| `MaxAuthTries` | `3` | не более 3 попыток за подключение |
| `LoginGraceTime` | `30` | 30 секунд на вход |
| `StrictModes` | `yes` | ключи не принимаются при небезопасных правах на `~/.ssh` |
| `X11Forwarding` | `no` | отключение графического канала |

Дополнительно скрипт:
- устанавливает права: `~/.ssh` — 700, `~/.ssh/authorized_keys` — 600, владелец — пользователь;
- запрещает запись в домашний каталог пользователя посторонним;
- на системах с SELinux (RHEL, Fedora) восстанавливает метки безопасности на `~/.ssh`;
- создаёт ключи SSH-сервера, если они отсутствуют;
- сохраняет копии изменяемых файлов в `/var/backups/ssh-hardening/`;
- применяет настройки без разрыва открытых подключений.

### 9.4. Свой набор настроек (`-c`)

Текстовый файл: одна настройка в строке, формат `Параметр Значение`, строки с `#` игнорируются. Файл полностью заменяет встроенный набор.
```
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
MaxAuthTries 5
```
```bash
sudo /usr/local/sbin/harden_ssh.sh -u "$USER" -c my_params.txt -n
```

### 9.5. Поддерживаемые системы

| | |
|---|---|
| Дистрибутивы | Ubuntu 20.04 и новее, Debian 11 и новее, RHEL / Rocky / AlmaLinux 9, Fedora; Devuan, Gentoo, Void |
| Требования | OpenSSH 8.2 и новее, bash 4.4 и новее |
| Старые системы (OpenSSH до 8.2, например RHEL 8) | поддерживаются: настройки записываются в начало `/etc/ssh/sshd_config` |
| Системы инициализации | systemd, а также системы без systemd (OpenRC, runit, контейнеры) |
| Alpine | после установки пакетов `bash coreutils shadow` |
| Не поддерживаются | macOS, FreeBSD |

Скрипт настраивает SSH-сервер, но не обновляет его. Устанавливайте обновления системы регулярно:
`sudo apt update && sudo apt upgrade` (Ubuntu, Debian) или `sudo dnf upgrade` (RHEL, Fedora).
